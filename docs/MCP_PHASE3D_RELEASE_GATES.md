## 2. G00：完整备份权限模型（独立上线安全决策）

### 2.1 已证明的现有行为

P3-C 正式 CI、D59/S 的合成环境中：owner 有效 R=true、W=true、F=false、scope=A/T，经明确意图创建 **一份完整业务数据库备份，含五条合成事项，包括范围外 B/T**。N3 无 W 请求返回 forbidden，且文件/表/审计/回执不变。该成功事实只证明现有实现，**不代表全量备份权限模型获准用于正式环境**。

源码依据：`src-tauri/src/mcp/service.rs` 的 R/W 门禁；`src-tauri/src/database/mcp_artifacts.rs` 的授权、意图、固定根、幂等/发布流程及 `VACUUM INTO`。backup 不接收用于裁剪输出的 format/filter/projection，scope 可参与请求身份/指纹，并未用于全量数据库导出过滤；没有额外 F 检查。因此“有 scope 参数或授权对象”不能证明备份按 scope 裁剪。

这里的 F 是字段完整读取权限，**即使改为要求 F，也不能未经决策就认定 F 自动授予跨事项 scope 的全库读取权**。备份含业务私密字段、历史及业务回执等；合成测试的“无凭证表”不等于“没有敏感业务数据”。安全凭证/DPAPI 存储与业务 DB 分开，不应把数据库内容或凭证上传补证。

### 2.2 逐层访问与生命周期审查

| 层面 | 现有证据/源码 | 尚未关闭的问题 |
|---|---|---|
| 谁可创建 | MCP 有效 R+W 和明确意图，无额外 F；D59 正向、N3 无 W 拒绝 | 哪些客户端角色获准创建全库，而不只是本 scope 备份 |
| 数据范围 | D59 内部读备份确认五条含 B/T；VACUUM INTO 是完整业务 DB | 范围外数据何时可被有 scope 客户端触发落盘，是否符合版本安全承诺 |
| 固定路径与文件 | `backup_dir/mcp-created`、生成文件名、private ACL、无 partial；D59/D60 正式隔离证据 | 正式安装路径/重定向/其他进程环境未实测，不能把合成路径验证外推为 L4 |
| OS ACL | `src-tauri/src/mcp/platform.rs` 用当前用户 SID 构造受保护 DACL，目录继承/文件复核 | 隔离边界是 OS 用户，不是 MCP clientId；同一 SID 下其他客户端/宿主进程可能存在文件访问路径，尚无实际攻击复现或排除证据 |
| MCP 入口 | 冻结 manage_business_data action 只有 backup/export；回传产物元数据，没有直接文件 read/download/list-backups/DB-restore/delete action | 没有这些 MCP action 不等于同用户客户端永远读不到文件，需结合其他路径审计 |
| CLI 入口 | `cli/parse.rs` data backup/export 经 authenticated IPC；`receipt get --kind artifact` 读回执元数据 | 未定位通用备份读/列表/数据库恢复 CLI 命令；不是对所有 OS/外部工具的安全隔离保证。事项 restore 不是 DB restore |
| GUI 入口 | `src/api.ts`、`SettingsPanel.tsx`、`lib.rs` 有 list/create/import/open-directory/delete/cleanup/restore backup 命令 | 软件本地入口不是按 MCP client scope 授权；本轮只审源码，没有操作 GUI 或验证这些动作的正式权限体验 |
| 列表、清理、恢复 | `database.rs::list_backups` 同时列根与 mcp-created 的 .db；`cleanup_backups` 按列表保留前五；delete/restore 校验根/子目录及普通 .db；restore 为校验后非破坏性合并，并先保留恢复前备份 | MCP-created DB 可能进入软件列表及清理/恢复路径，需明确是否允许、保留和删除责任、异常恢复。不能只看 MCP 无读取接口就关闭风险 |
| 自动保留 | `database.rs::prune_backups` 对顶层 auto.db 的保留逻辑不同；作业 7/30 天是另一套机制 | 不能把 auto 保留或 job TTL 当作 MCP-created DB 的完整保留政策；需决定期限、数量、清理与回执/文件一致性 |
| 审计与未知结果 | 产物作业/回执、成功创建审计、原幂等键不重生文件的既有测试 | 未证明每次文件打开、列表、删除、清理均有审计，也未完成正式环境孤儿文件/失败恢复闭环 |

以上同用户潜在访问风险属于需要安全设计决策和调查的边界，不声称已运行验证越权读取。本轮没有打开正式备份、扫描正式目录或进行攻击测试。

### 2.3 供用户单独选择的创建权限方案

以下是设计选项，不是实施授权；本轮不选择、不删功能、不改 API。

| 方案 | 优点 | 代价与仍需解决的问题 |
|---|---|---|
| A 保留 R+W+明确意图，明确批准此角色可创建全库 | 兼容当前实现，自动化路径变化最小 | scoped writer 可触发范围外数据落盘，必须明确接受全库角色语义并约束文件访问；普通 W 不宜被默认为全库授权 |
| B 增加 F，同时保留 R+W+明确意图 | 与敏感字段读取条件更一致，门槛较当前明确 | F 仍可能只适用于 client 的事项 scope，不能单靠 F 解决跨 scope 全库授权；还需全库角色/范围决策 |
| C 独立完整备份能力/管理角色或 client allowlist，并明确全库确认 | 可将普通写入与全库备份分开授权，审计责任清晰 | 需要另批产品/协议/UI/迁移及测试；不能擅自以现有 F/W 代替新能力 |
| D 只在软件端受控执行完整备份，MCP 保留受限入口策略另议 | 减少 AI 客户端触发全库落盘的路径 | 自动化能力和现有契约受影响，需要另行设计审批/兼容方案；本轮不能直接移除 backup |

无论选何方案，均需分别决定：允许角色与跨 scope 数据范围；同 SID 文件访问边界；落盘位置/ACL/文件名与元数据暴露；保留数量和期限；删除/清理责任；创建和后续访问的审计；发布失败、未知结果、恢复与孤儿资料处理。不能把权限选项与生命周期规则合并成一次含糊“接受风险”。

**关闭条件：** 用户单独确定权限和文件生命周期方案；按决策另批最小实现/测试（如需要），取得授权正向/拒绝、范围外哨兵、敏感字段、同用户路径与 GUI/CLI/MCP 入口边界、回执/审计/失败恢复的相应证据；明确正式环境适用性。在此之前 G00 不关闭。

## 4. G06：真实 GUI 与软件审批边界

- **现有证据：** D56/S 真实 MCP 申请→needs_user_approval，批准前标题未变；既有一次 `db.mcp_resolve_undo(true)` 软件端自有批准模拟，标题版本 0→1→2、补偿审计保留。多日期/截止整批规则有 PDATE/PDEADLINE L1 和 C5B CLI pending。

## 5. G01：复杂事项 action/mode

- **证据/缺口：** D39–D43、D47–D55 共 14 行缺直接 stdio 成功：setUrgent、recordWorkEvent、createSubtask、setParent、reorderSubtasks、queue/reopen、moveUp、moveDown、reschedule、archive、trash、restore、correctWorkEvent、voidWorkEvent。已有 W/P 领域或 C4/C4W CLI 证据各不相同；moveDown 未定位独立 L1/CLI 专项。私有 cli_create_subtask 不是 mutate_task.createSubtask，correct 使旧事件作废也不是 voidWorkEvent 端点成功。
- **影响/场景：** 办理事实、层级/间接 scope、队列顺序、日程、回收和历史纠错，可能影响编号、版本、审计与授权。不能从 create/patch 成功推导全部写入可靠。
- **承诺/建议：** 冻结契约公开这些 action，正式版本承诺范围待用户确认；若宣称相应能力完整可用，建议条件性阻断该能力的完整验收声明/上线。
- **关闭条件：** 对实际承诺的缺口取得直接 stdio 已知前后状态、编号/事件/审计/幂等/失败原子性和权限范围证据；字段/状态组合按实际风险选择，不要求全部笛卡尔组合。
- **最小后续授权：** 先选 action 与最小夹具，固定字段、编号、key、时间与办理意图。复用已有领域 oracle；涉及事项写入/事件/层级/日期，不得因合成环境就推定已授权，审批部分引用 G06。

## 6. G02：非空增量和事件模式

- **现有证据：** T1 直接 current 初始/空增量；S 默认 events 初始/空增量；JCUR current 分页及非空 edited、JCH 默认 events removed 仅 ID/不泄正文、CLI C5F current 非空。不能按测试名误认 JCUR 测了 events。
- **缺口：** 已知变更后的直接 stdio current 成员/版本；移出范围 removed 的模式专属读取；events 非空逐事件/不合并/分页 oracle。空数组不证明这些内容正确。
- **影响/场景：** 增量消费者漏变更、误重放或收到移出范围正文；同步一致性与隐私边界。
- **承诺/建议：** 指南描述 current/events 两种同步；若完整增量是本版本承诺，关键非空 L3 是条件性门禁，否则须用户明确限定范围，不能自行延期。
- **关闭条件：** 各 mode 自己的 cursor、独立已知 ID/版本/事件序列/removed 无正文、重放稳定及必要分页核验。
- **最小后续授权：** 优先复用一个已获批写入的前后只读请求；如必须重建变更或改 scope，另列最小写入/授权变更，不为只读补证自动执行。

## 7. G03：inspect 分支和独立重算

- **现有证据：** D14/D15 health/trace L3；QT compare 是旧 snapshot 与新数据 dataVersion 差异，C5F 同 report 空差异及 cache 只有 CLI 辅证；cache 暂停拒绝有 L2。
- **缺口：** compare/cache 专属直接 stdio 成功；recompute 独立正向尚未定位。summary explicitRequery 与 repair/clear API 均不能代替 recompute。
- **影响/场景：** 数据解释/质量诊断、缓存与统计重算；实现存在而无端点证据可能造成诊断结果被错误信赖。不能授权任意 SQL/修复来补证。
- **承诺/建议：** 指南支持这些 action；公开完整 inspect 时建议条件性阻断，recompute 先确认实际契约/成功输出，而非默认只差套一层测试。
- **关闭条件：** 固定已知统计 1/0 的成功输出、同/异 basis 比较、缓存状态 oracle、重算不改变业务内容，保持现有限制/权限；相应直接 stdio 证据。
- **最小后续授权：** 独立合成只读环境，最多三条缺失 action，并提前核算 snapshot 预算；不执行业务写入或 repair，不增加框架。

## 8. G04：CSV 与后台导出

- **现有证据：** D60/S 同步 JSON 一份四条范围内事项、无私密字段；FEXPORT 同步 CSV L1 有公式单引号断言；JX 异步 CSV L2 有发布恢复不重生成，缺意图只断 is_err，未证精确码。
- **缺口：** 同步 CSV、job-export 各自直接 L3；实际文件的范围/字段/公式/引用与换行独立 oracle，不能外推所有文本组合。JSON 与后台 CSV 不是同一端点成功。
- **影响/场景：** 电子表格打开导出、范围外/敏感字段泄漏、公式执行、未知结果重复产物与残留文件。
- **承诺/建议：** 协议存在对应格式/作业 kind；若本版本承诺 CSV/后台导出，建议条件门禁；否则由用户决定支持范围，不能因 JSON 通过自动关闭。
- **关闭条件：** 精确格式/字段与已知合成行、转义/公式、固定根/ACL、文件数、complete/无 partial、拒绝不落盘与原键恢复；各真实 wire 路径分别记录。
- **最小后续授权：** 全新合成文件夹具同步 CSV 一请求一文件；异步路径另给明确 job/请求/文件预算，共享文件安全 oracle，不在原 C 两文件夹具加产物。涉及文件生成，须另批。

## 9. G05：正向在途 cancelJob

- **现有证据：** D33/BJ 在 job 已 completed 时取消 waiter；D34 无意图 cancelJob 返回 explicit_intent_required 且状态不变；JC 的 local_cancel 是内部 L1。
- **缺口：** 真实 queued/running 状态下自有 job 的正向 cancelJob、最终状态/结果与其他 job 隔离。不能把取消 waiter、内部 cancel 或取消已完成 job 作为通过。
- **影响/场景：** 用户停止长任务、资源消耗和共享 waiter；误杀或继续运行可能违反用户预期。
- **承诺/建议：** 指南有 cancelJob，实际字段是 `explicitUserRequest`；若承诺在途取消可靠，建议条件性阻断，当前未验证状态继续保留。
- **关闭条件：** 先真实观察在途，再明确一次取消，并独立核对终态、result、未误杀其他任务；保留取消时完成的事实，竞态完成不可改称在途。
- **最小后续授权：** 一只读作业、一自有明确取消和有界状态/结果查询；先证明现有合法可控点，不新增产品钩子、伪造状态、盲目睡眠竞态或修改资源限制。不能保证真实在途时应报告未覆盖。

## 10. G07：其他 job kind 与 S01 调查

- **现有证据：** query_tasks L3 完整最小生命周期；report JR L2、export JX L2；history/calendar 源码支持，未定位专属 L2/L3。JRET service 证明权限/scope 变化，但 7/30 天是内部清理核验，不是 MCP result_expired 请求。恢复/保留/资源边界未全部直接 L3。
- **S01 源码事实：** `cli/advanced.rs:179` 附近 start 白名单含 list_report_items、不含 query_task_history；`mcp/jobs.rs:863` 附近分派含 history、不含 list_report_items，指南列五 kind 包括 history。输入外围条件合法时，可能出现 CLI history 提前拒绝或 report-items 到宿主后 unsupported；**该运行后果是推断，本轮没有运行复现**。
- **影响/场景：** 不同客户端入口的后台历史/统计/日历/导出使用，兼容性和运维预期；result 失效/恢复不当可能返回陈旧结果。S01 不能仅归为“缺一条测试”，也不能无复现就断言已确认运行缺陷。
- **承诺/建议：** MCP 五 kind 在指南/源码中存在；CLI 是否计划提供完整同集合待用户/设计确认。先调查 S01，承诺的其他 kind 和关键恢复路径为条件门禁，不机械复制所有算法测试。
- **关闭条件：** 明确入口支持意图；必要时独立最小复现并另批修复/验收。其余 kind 复用共享算法，取得已知输入输出和真实 job 端点；保留到期/恢复/权限关键边界的正确层级。
- **最小后续授权：** S01 先纯参数层或隔离只读复现；history/calendar 建立已知成员，report 复用 JR；export 归 G04 文件预算。涉及只读 job 和可能文件，需按具体 kind 另批，不调度写工具。

- **影响/场景：** 同一客户端连续统计/分页/日历/诊断触达限制；可能影响可用性，当前不是已确认安全缺陷。
