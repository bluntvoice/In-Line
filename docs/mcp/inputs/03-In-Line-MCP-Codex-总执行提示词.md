# 可直接交给 Codex 的 In-Line MCP 总执行提示词

> 使用方式：将此提示词以及配套的 `01-In-Line-MCP-PRD-144项完整需求.md`、`02-In-Line-MCP-分阶段开发与验收方案.md` 一同提供给 Codex，或先把两个需求文件放入仓库 `docs/prd/` 并让 Codex 阅读。**仅发送本提示词而不给配套文件，不足以让 Codex获知全部144项具体约束。**

---

你现在负责扩展 In-Line（仓库：`https://github.com/bluntvoice/In-Line`）的本地 MCP 能力。这是现有 Windows/Tauri + Rust/SQLite 桌面软件的**受控迭代开发**，不是重新创建新项目。

## A. 权威输入及优先顺序

请先完整阅读：

1. 本指令与我已提供的《In-Line MCP 扩展开发 PRD（144 项已确认需求）》；
2. 《In-Line MCP：分阶段开发、验收与发布方案》；
3. 仓库最新 `AGENTS.md`（以及本地适用的全局 AGENTS）、`docs/prd/*.md`、README、CHANGELOG、RELEASE_NOTES；
4. 现有 `src-tauri/src/bin/in-line-mcp.rs`、`src-tauri/src/database.rs`、`src-tauri/src/lib.rs`、models、前端管理页面、测试和 `.github/workflows`。

用户对144项的最终选择是需求权威；如当前代码或文档与其冲突，先列出具体冲突、影响及建议，**不得擅自改写决定**。注意以下**明确选择**：

- 所有 MCP 工具包括原有两个只读工具均需独立客户端认证；常规读取权限组默认开、完整读取与写入默认关，具体客户端必须授权。MCP 只提供本机 stdio，不开外网服务。
- 新增写入必须通过主程序共享领域逻辑，支持状态/加急/队列/未来事项/子任务/归档/软删除/办理记录/批量等；不开放永久删除、清空回收站、数据库覆盖/恢复、附件文件操作。
- 每个混合批次默认20个事项，整批原子事务；Dry Run、消歧、幂等、字段冲突、操作前后审计及用户批准撤销必须完整。
- 全历史与结构化统计、增量游标、事件/当前状态两模式、失效重同步、报表溯源、健康检查以及脱敏诊断按 PRD 实施。
- 后台任务摘要保存30天、临时结果7天；临时限流导致的暂停最长30分钟；进程异常后的可靠检查点恢复窗口24小时；只读基准失效允许完整自动重查最多一次，业务写入绝不因中断盲目重放。
- 短期统计缓存依数据变化失效；内存优先，必要时磁盘，**用户选择不额外加密磁盘缓存，仅使用 Windows 文件ACL**，需最小化敏感数据落盘。
- 已发布旧 MCP 接口允许下一正式版本直接移除，无须90天兼容期，但须披露破坏变化和迁移方式并事先征得用户确认；现有读接口首次强制认证也是明确的安全例外。
- 故障管理只做**基础状态筛选**，不要做多条件搜索；故障资料导出**不生成 SHA-256 校验清单**（但 GitHub 更新安装包 SHA-256 digest 校验仍必须照仓库规范）。
- 故障摘要默认恢复后30天保留、普通故障允许用户静音7天、复发识别基线为滚动30天内3个相关独立轮次；P0/P1不可静音或带缺陷发布。
- 故障手动脱敏导出 CSV/JSON、简短诊断概述、预览确认、标准化 Codex 排查提示词、可信版本/Commit 元数据。不得自动上传、自动调用 Codex 修复或导出原始完整技术日志供 AI 自由读取。
- PRD 有144条，**必须逐条对应需求编号、实现、测试、证据和验收状态**；不要只实现摘要中列举的高优先级项。

## B. 启动工作：必须先执行 Phase 0，仅审查和规划

1. 检查 `git status`、当前分支、本地 `HEAD`、远端 `origin/main`，同步最新仓库时仅允许安全快进；存在未提交修改或无法安全同步时先报告并保护当前工作，不能硬重置、强推、清理未跟踪文件或覆盖用户代码。
2. 真实读取现有代码和 PRD，确认当前 MCP 工具数、通信方式、数据库读写路径、队列/历史/统计/备份规则、UI通知与 Actions。不要假定事先描述的仓库快照仍是最新状态。
3. 评估新 MCP sidecar 如何验证每个客户端凭证，并安全请求主程序执行写入；必须处理 Windows 单实例/静默启动、数据库写入协调、UI刷新、stdio stdout纯协议输出、多客户端交错调用。
4. 输出包含完整 144 条的需求追踪矩阵，按 P0–P9 分配到开发阶段，列出“现有可复用 / 需修改 / 需新建 / 被现有机制阻碍 / 尚待验证”，不得将未测试内容称为已实现。
5. 给出 API 草案（领域分组，不滥增工具）、权限/身份/范围模型、持久凭证及审计储存边界、备份/迁移保护方案、任务/游标/版本数据结构、隔离测试策略、风险评估和阶段验收标准。
6. 对先前确定的三大边界尤其严谨：**真实业务规则不可被 MCP 旁路重写**、**认证与权限数据不随业务备份恢复**、**危险数据库/写入操作不得通过异常重试重复执行**。
7. Phase 0 审查与文档草案完成后，提交**只读现状分析、架构设计、阶段计划、差距矩阵及需要用户核验的事项**，然后**停止，等待我的明确验收**。除非我另行批准，此时不得开始 Phase 1 或更后续功能实现，不得自行 Commit、Push、Tag 或 Release。

## C. 之后每一阶段必须遵循的固定工作流

只有我明确宣布“当前阶段验收通过，可以提交并推送，进入下一阶段”后，才允许：

- 复核变更范围与测试证据 → Commit → Push → 建立不可移动的 `mcp-phase-XX-accepted` 阶段 Tag（确认不会触发正式发布）→ 向我报告 SHA 和 Tag → 开始下一阶段。
- 在此之前，你只能完成本阶段的改动、隔离测试、文档及验收报告；未通过验收严禁擅自转阶段。
- 每阶段都应执行项目规定的 `npm.cmd test`、`npm.cmd run build`、`cargo fmt --manifest-path src-tauri/Cargo.toml -- --check`、`cargo test --locked --manifest-path src-tauri/Cargo.toml` 及本阶段相关的 API/stdio/SQLite/多客户端/安全测试；高风险改动还要在隔离环境构建 NSIS 安装包，验证安装升级和旧数据。
- 任何测试未执行，要标明“未执行”而不是“通过”；CI 偶发失败要保存首次失败和重跑证据。关键安全/事务/数据测试不得凭重跑放行，非关键不稳定测试仅在我批准替代验证与恢复条件后方可暂时隔离。
- 报告必须包含需求覆盖表、文件级修改摘要、运行命令和结果、关键负面用例、性能/风险、已知问题、下一步建议，明确请求我验收。
- 优先 CLI、自动化与现有 MCP 能力验收；GUI 只作不可替代的交互和安装验证。界面紧凑，不增加大按钮、冗余横向栏位、过大留白、过多分割线或无必要独立页面。
- 代码改动影响功能时，同步更新 README、CHANGELOG、相关 PRD/API 指南。保持仓库既有 SemVer、CI/开发构建/预发布/正式 Release 分层与更新渠道逻辑；**任何正式版本与 GitHub Release 都需我单独批准**。

## D. 发布、热修复和安全控制

正式版必须先通过全部需求覆盖与跨阶段集成验收，再执行 Actions、NSIS、旧数据升级、MCP sidecar、客户端授权/迁移、数据库备份/恢复保护、软件内更新等发布清单。P0/P1 阻断发布；低风险已知问题只有在我明确接受后才可留存。重大问题可采用针对性热修复，但安全、数据完整性、相关回归、安装升级及我的确认不能跳过。

已确认的故障尽可能通过独立 Git Worktree 和隔离数据库复现；先核实当前分支是否仍受影响，经我确认才迁移修复。新增或完善长期回归测试，不得通过静默删测试或削弱断言获得虚假的 CI 通过。

## E. 本轮你的第一次回复必须交付

1. 最新 Git 基线（分支、HEAD、工作区状态及同步结论）；
2. 当前代码已实现的 MCP 能力与安全/架构缺口；
3. 144项需求覆盖矩阵的位置，以及阶段 P0–P9 的映射；
4. 关键架构技术方案及需要关注的风险与冲突；
5. Phase 0 完成后的验收证据与下一步建议。

**严格注意：第一次仅执行 Phase 0，不要跳过我的验收直接开始开发，也不要自行推送仓库或发布版本。**
