# In-Line MCP：分阶段开发、验收与发布方案

> 配套需求文件：`01-In-Line-MCP-PRD-144项完整需求.md`。本文件为实施建议，阶段拆分和内部技术路线可以基于真实代码评估优化，但不得降低已确认的需求与安全边界；调整阶段必须先说明并取得用户批准。  
> 当前状态：**尚未开始实施，任何阶段不得标记已完成。**

## 一、执行规则（整个项目一直生效）

**顺序门禁**：安全同步最新仓库 → 核对既有 PRD/架构 → 本阶段实施 → CLI/单元/集成/必要 GUI 验证 → 交付逐项验收证据 → **停止等待用户明确验收** → 验收通过后 Commit + Push + 固定验收 Tag → 才可实施下一阶段。正式 Release 只有最终集成验收及用户另外批准后才能创建。

- 每阶段应维护需求追踪矩阵，字段至少：编号、功能说明、实现阶段、代码文件/函数、测试用例、验收条件、证据、状态（未开始/进行中/待验收/通过/失败/明确延后）、用户确认、Commit SHA、阶段 Tag。
- Phase 0 基线审查**只允许只读检查及起草文档**；任何已有未提交修改都要保护，`git pull` 仅在安全可快进且不覆盖修改时执行，严禁 `reset --hard`、强推、清理用户未跟踪文件。
- 推荐研发流程：开发期仅使用本地隔离数据库和 MCP stdio 测试子进程；UI 非必要不通过 Computer Use 验证。优先 `npm.cmd test`、`npm.cmd run build`、`cargo fmt`、`cargo test`、集成测试和真实 NSIS 测试。
- 高风险环节（认证、持久授权、事务、备份、恢复、后台任务、进程启动）需负面/异常路径测试，覆盖越权、授权撤销、重复重试、进程中断、快照过期、并发冲突、写入部分失败等。
- 任何一阶段被用户拒绝验收：暂停下一阶段，针对性修复与回归，再重新提交证据；用户批准前不得 Commit/Push 当前阶段。影响既有阶段时补充历史需求复验。
- 每阶段的 Tag 可使用 `mcp-phase-01-accepted` 等非 SemVer 名称；Tag 指向该阶段通过验收后推送的不可改动 Commit。**不创建 Release**。如 GitHub Actions 对 Tag 有触发规则，先核验不会误触发发布。
- P0/P1 发布缺陷强制阻断，P2/P3 只有明确披露和用户批准才可带入正式版。严重故障热修复保留关键安全/升级检查。

**跨阶段需求说明**：某些需求在前面阶段先实现机制，在后面阶段补全管理界面或性能保障（例如 P1 授权限流与 P5 在途任务处理；P3 审计写入与 P7 导出；P5 增量事件与 P6 索引和健康）。一个条目只有所有对应验收点都通过，才可标记为“全部实现”。

## 三、阶段验收包统一格式

每个阶段交付以下内容，可使用 `docs/mcp/acceptance/PHASE-XX.md` 等明确路径（名称以现有仓库目录标准为准）：

1. **基线与变更**：开始时仓库分支、原始 HEAD、改动范围、实际修改文件、数据库 schema 或 API 变化。
2. **逐项需求覆盖**：要求编号 → 实现函数/文件 → 测试 → 证据 → 状态；不得将仅规划的项目标记完成。
3. **测试证据**：命令、退出码、测试数及失败明细；编译日志和必要时隔离测试数据库完整性检查。
4. **异常与安全**：明确越权请求、撤销后访问、并发冲突、幂等重试、批次事务原子性、迁移备份、进程重启等用例。
5. **未完成与风险**：失败和跳过项目、原因、影响、计划；任何 CI 重跑成功也必须保留首次失败证据。
6. **请求用户验收**：交付报告后停止等待；收到明确通过才能 Commit / Push / Tag。输出提交 SHA、推送目标分支和 Tag 以及对应证据。
7. **文档同步**：同时检查 PRD、README、CHANGELOG、相关操作指南/API文档，不能把未发布功能当正式功能宣传。

## 四、建议的关键自动化测试清单

| 类型 | 最低覆盖 |
|---|---|
| 认证/限域 | 未认证拒绝、旧工具也认证、三组权限默认值、每客户端撤销轮换、备份恢复不复活授权、部门/类型读写两侧限制、暂停优先级 |
| 领域写入 | 创建/幂等、字段冲突、精确消歧、状态/加急、工作事件真实统计、队列编号、未来事项、父子两级、归档/软删除/恢复、禁永久删除 |
| 批量事务 | 混合操作原子提交/整体回滚、含歧义整批不执行、20条限制、跨请求限流、Dry Run与实际差异、成功后核验 |
| 长任务/恢复 | 同客户端复用、跨客户端隔离、取消单调用与取消任务、全局暂停/撤销、30分钟暂停、24小时异常恢复、数据基准失效、最多1次完整重查 |
| 增量/健康 | 游标不漏事件、事件与最新状态、历史缺口、代际变化、全量重同步、索引重建验证、已知缺口准确标识 |
| 缓存/报告 | 查询结果与UI口径匹配、缓存复用及版本失效、权限变更即失效、内存/磁盘边界、磁盘ACL、手动清理不破坏文件与检查点 |
| 诊断/导出 | 关联编号、只读脱敏、故障轮次与恢复证据、7天静音、30天摘要保留、基础状态筛选、CSV/JSON脱敏预览、Codex提示词和版本元数据、不产生哈希清单 |
| 兼容/发布 | 原两工具认证迁移、接口契约检查、静默后台单实例、全量新旧回归、NSIS安装与更新、旧库迁移前备份、GitHub Actions/Release标准 |

## 五、明确不在本轮实施的事项

无外网MCP服务、无实时订阅推送、无附件文件API、无 AI 自动数据库修复/恢复、无应用内全新定时调度器、无跨设备同步、无跨客户端共享数据、无完整分布式调用链、无高级故障筛选、无故障导出哈希清单、无普通用户磁盘缓存加密密码配置。

## 六、正式交付判定

只有满足以下条件才可申请最终发布验收：

- 全部 144 项有对应结论，待实现/待验证未被伪装成通过；确需不实施的项目须先获用户明确修改 PRD 的批准。
- 每阶段验收证据、Commit、固定阶段 Tag 可追溯；正式发布前完成独立跨阶段集成验收。
- P0/P1 为零；已接受的 P2/P3 有影响说明、修复安排与用户批准。
- Windows 安装、从现有正式版升级、原数据库/备份/权限迁移与安全回退预案实际验证；所有测试使用隔离或安全备份的数据，不改动真实业务数据。
- 正式版本号、Release Notes、更新渠道和安装包文件获得用户**另一次明确的发布授权**。
