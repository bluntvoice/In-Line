## 1. 定位与目标

将 In-Line 现有的本地只读 MCP 报告服务，扩展为在独立授权、可审计、可回滚、遵守领域规则前提下的本地 AI 事项协作入口。用户在 AI 对话中可查看、统计、检索、管理日常事项；软件现有图形操作、数据库完整性与队列规则不得受破坏。

**已核查的代码事实**（以下均为开发前快照）：

- `src-tauri/src/bin/in-line-mcp.rs`：当前通过 `rmcp` + stdio 提供 `get_report_summary`、`list_report_items` 两项只读报告接口，现有 `list_report_items` 接口允许分页上限 500；本次约定新统一上限为 100，需要按有意兼容变化与文档迁移规则处理。
- `src-tauri/src/database.rs`：`open_reporting()` 以 SQLite 只读方式打开当前业务库；普通主程序数据库有迁移、备份和实际事项领域逻辑。
- `src-tauri/src/lib.rs`：Tauri 命令调用数据库领域操作，并在写入成功后发布 `data-changed` 事件。MCP 新写入不得仅为方便而自行绕过领域逻辑直接操作 SQLite。
- `AGENTS.md`：仓库对 PRD、Git、开发构建、CI、Tag、发布、安全备份与本地验证已有明确要求。先遵守最新仓库约束；如与本 PRD 的具体需求冲突，先向用户说明并提出兼容修订，不擅自更改产品决定。
- 工作日历 PRD 定义的是基于真实历史的只读回顾视图；本 MCP 的未来计划能力应借助现有事项接口，不应擅自改写工作日历产品定位。

## 2. 不可协商的总体边界

1. **部署**：仅本机 stdio；不增加 LAN、远程 API、云服务或外网监听。可以被已经授权的外部 AI 调度器调用，但 In-Line 不自行新建定时任务引擎。
2. **授权**：所有 MCP 工具（含原有两项只读）在本次发布后均要求客户端身份认证；**常规读取组默认开，不等于匿名可读**。完整读取和写入组默认关闭，客户/部门/事项类型范围由服务端强制执行，授权撤销立即生效。
3. **业务权威来源**：唯一受信任的事项业务规则为主程序领域服务、现有数据库结构及 PRD。不能靠 MCP 侧另一套 SQL 写逻辑模拟队列、办理记录或归档。
4. **绝对禁止**：MCP 永久删除事项、清空回收站、直接覆盖/恢复数据库、绕过鉴权、自动调整授权、安全设置或恢复备份、跨客户端互读任务及诊断、自动操作附件/文件、擅自把诊断传给第三方。
5. **用户明确意图**：高影响批量操作、归档/软删除、修改业务记录、设置未来日期、添加/拆解子任务、触发备份等，仅在明确指令和相应授权下进行；无歧义事项按稳定 ID 操作。
6. **事务与审计**：混合批量操作必须原子提交；操作前后差异、AI 解释及结果长期审计；用户批准的撤销与崩溃后的自动事务回滚严格区分。
7. **UI**：紧凑布局、适度留白、合并通知、不弹 Windows 系统通知，不将大量高级选项暴露为独立设置。
8. **工程纪律**：阶段明确、测试先行、用户验收后才能 Commit / Push / 阶段 Tag / 下一阶段；仅在全量集成验收与批准后进入正式发布。

## 3. 功能范围与详细规则

### 3.1 客户端认证、权限和状态

- 全局三个组：`常规信息读取`（默认启用）、`完整信息读取`（默认停用）、`日常事项写入`（默认停用）；每客户端独立长期凭证与即时轮换、撤销；按部门/类型可选限域；MCP 全局暂停持久化且优先于普通进程退出。
- 一次有效授权后，同一授权范围内正常操作不再逐笔弹窗；不得将此等同于授权 AI 处理需要用户额外明确意图的高风险事项，亦不授予自动撤销、修改授权等操作。
- 客户端初始化向 AI 提供真实 MCP 版本/能力/可用工具及权限错误类别。旧客户端必须在首次启用认证后的新正式版本更新连接配置。
- 凭证、权限组、暂停设置与业务数据备份分离。普通备份恢复可以按已验证规则合并业务偏好，但不能复制、恢复或激活历史客户端凭证。
- MCP 需要按需启动主程序并静默处理写入，通过单实例/受信任 IPC 协调写操作，保持 UI 不抢焦点；不同客户端读写并发按全局领域事务协调。
- 对连续认证失败和异常高频调用实行分级短暂限流；未认证请求不应因此反向锁住无辜已授权客户端。用户撤销授权不能被冷却期结束自动恢复。

### 3.2 事项查询与报告

- 现有只读报告工具保留业务含义，但新增认证，分页上限按新规范控制为 100；接口层应提供兼容错误/迁移说明，不误导旧客户端。
- 支持完整历史、组合条件、稳定分页、时间线、待办/暂缓/已完成/归档/回收站/作废事件的授权读取。默认统计口径计算有效的归档历史，排除回收站及作废工作事件。
- 报告面向日、周、月、自定义日期范围，返回**结构化统计数据**、计算口径、数据覆盖范围、快照、完整性和已知缺口，由 AI 自行生成文字报告。指标可按需追溯事项与有效办理记录。
- 支持在明确用户请求下保存命名查询条件，但模板不能保存或绕过扩大的数据访问权限。语义相关性分析须区分事实与猜测，不自动写入关联字段。
- 使用受控数据快照/数据版本保证同一逻辑查询跨页一致；无法验证则报失效，不将不同数据代际混算。统计数值与界面不同须先比较范围、日期、权限和快照，再定位具体差异，不改写业务数据“对齐”统计。

### 3.3 事项写入与队列

- 允许 AI 根据明确指令创建、局部修改、设置状态与加急、设置截止日期、追加真实办理事件、办理事件纠错、归档、移入回收站、恢复、处理子任务/关系/排序和批量事项操作。永久删除无 MCP 接口。
- 新建前重复检索只做提示，不擅自合并。重试采用幂等标识；更新事项使用稳定 ID；同一字段的并发修改拒绝并标明冲突，不同字段可按领域约束合并。
- 多个候选事项无法唯一定位时必须请求用户消歧；在混合批次中，任一目标不确定就停止**全部批次**，不得先执行部分。
- 已符合目标状态的操作跳过，不额外生成业务事件、重复计量或队列副作用。仅当真实业务规则将重新入队等视为独立行为时按实际指令操作。
- 仅在用户明确授权时优化既有队列；未来事项遵循本项目原有的日期、取号、延迟入队及跨日规则；不得擅自更改号码。子任务最多两级，父子状态、编号、排队完全独立。
- 混合批次全有全无，默认每次最多 20 个事项（用户可调整），有时间窗口累计频率限流；Dry Run 返回逐项差异，不修改任何业务信息。
- 成功提交后核验关键状态；若写入已提交但后置核验失败，则要报告“已提交、核验异常”，只允许低风险技术恢复，绝不能补偿性盲目二次写入。
- AI 提出的历史撤销申请必须经用户在 In-Line 侧批准，结合当前数据冲突校验；自动事务回滚不等于 AI 自主撤销。

### 3.4 变更增量、任务和恢复

- 变更事件按可靠序号/游标而非仅更新时间提供；事件流、按事项聚合最新状态两种模式。创建/修改/状态/归档/移入回收站都需覆盖；对于权限收窄或离开条件的事项，可安全返回无敏感内容的必要删除/脱离范围标记。
- 游标失效、记录缺口或数据库数据代际变化时明确报错并引导当前事项全量重同步；不能造出丢失的事件。派生变更索引按需安全重建，与长期审计储存分离。
- 复杂只读查询/统计/导出可转后台任务；客户端查看进度、取消。任务摘要保留 30 天，临时结果保留 7 天，已正式导出的文件另行保留；普通客户端断开不必终止任务，全局暂停和撤销授权须按安全规则阻止继续读取。
- 临时限流生效时拒绝新请求，事务安全提交或回滚；长任务在检查点暂停或受控取消。限流暂停最长 **30 分钟**，重复触发不能无限续期。解除后须重新验证客户端授权、快照、期限才能安全续执行。
- 进程异常退出/电脑重启，仅对已持久化检查点和可验证一致数据基准的只读/导出任务恢复；恢复窗口 **24 小时**，不能因重启无限延长；绝不自动重放业务写入。
- 原数据基准失效时，终止旧任务；若原始指令允许最新数据，仅可自动完整重查 **1 次**，再次失败停止。新旧执行关联同一请求但保留独立记录，最终结果只采用完整有效轮次。
- 同一客户端严格等价的在途只读任务可复用，同一任务的多个等待调用取消互不影响；取消整个任务必须有明确指令。跨客户端不共享。已完成结果仅当数据/口径/权限/TTL 仍有效且用户未要求重查时才复用。

### 3.5 数据健康、缓存、统计可追溯性

- 提供轻量只读健康检查：变更序号、游标有效性、数据代际、已知缺口、缓存状态，不能声称绝对完整，不自动修业务记录。
- 统计返回完整性标志、范围、快照、历史缺口、缓存来源及有效性；提供指标对应事项/事件/计算式的分页追溯。
- 内存优先、确有性能收益时才使用磁盘缓存；数据变化驱动失效 + 短 TTL + 容量限制 + LRU 类淘汰。重启后磁盘缓存必须重新验证。
- **用户已明确选择：磁盘缓存不增加内容加密，只依靠当前 Windows 用户专属目录的文件权限。** 因同账户进程和文件复制风险，应尽量不持久化事项正文/备注/敏感信息，禁止把缓存视为密钥或授权存储；有安全风险无法合理控制时不落盘，而非擅自加密改变选择。
- 管理页展示缓存占用和一键清理；只清可再生缓存，不删正式导出、任务检查点、审计或业务数据。空间超限先自动清理，持续异常才轻提示，磁盘不足时业务库安全优先。

### 3.6 诊断、故障管理和导出

- 技术诊断独立轮转，不混入长期业务审计。请求、任务、执行轮次、错误、审计使用关联标识；诊断保存期限可以较短，但不得自动删业务审计。
- AI 只可按错误编号读取**自身请求的脱敏诊断**；完整技术日志与原始堆栈仅用户本机查看或主动导出。低风险自动恢复只含既定且有限的只读/连接技术措施，高风险业务或权限修复不允许。
- 相同故障按客户端/模块/类型/证据聚合，保留轮次；必须经相关功能实际成功验证才可标记恢复。已恢复又复发，建立新轮次而非覆盖旧轮次。
- 默认滚动 **30 天**至少 **3 个相关独立故障轮次**提升关注级别；这不自动改变 P0/P1 缺陷级别或 AI 权限。
- 已恢复故障摘要默认 **30 天**后自动清理，可手动归档/清理；未解决故障不能因期限届满而自动消失。一般未解决故障可由用户静音 **7 天**，风险提升解除静音，P0/P1 不可静音。
- **用户已明确选择**：故障管理只支持基础状态筛选，不新增多条件组合过滤和关键词搜索。
- 用户按状态手动导出脱敏 CSV/JSON 故障摘要，各轮及错误编号有据可查，自动附简短事实/待验证假设区分明确的排查建议；导出前自动脱敏、预览、用户确认，实际写入必须与确认内容一致。
- **用户已明确选择**：不生成 SHA-256 故障文件校验清单或签名，仍必须检查文件生成成功。注意：这不取消仓库 `AGENTS.md` 所要求的**软件更新 Release Asset SHA-256 digest 校验**，两个场景互不相同。
- 同时生成可供用户交给 Codex 的简洁排查提示词，不自动调用 Codex。记录故障发生时与导出时的软件、MCP、数据库版本及可核实 Commit SHA，缺失不得猜测。

### 3.7 UI 与工作范围排除

- MCP 客户端管理只提供简洁的独立授权、权限、最近访问/结果、异常、连接测试/兼容指引；不误将最近访问显示为在线。
- UI 优先紧凑、少按钮、不过度留白、不额外增加长列表/单独故障分析面板；通知轻量合并。
- 本轮**不包含**：附件和文件绑定、外网 MCP 服务器、跨设备同步、实时变更推送、完整监控告警中心、客户端自动修改第三方配置、独立日历调度器、永久删除 API、AI 自行恢复数据库。

## 4. 验收与发布的硬性规则

- 每条需求有唯一追踪 ID、实现文件、自动/人工测试、验收结果、用户批复与 Commit/Tag 链接。尚未验证的现有代码必须标记 `待核验` 而不是 `已完成`。
- 每阶段提交验收包；**测试/用户验收未通过时禁止进入下一阶段**；通过后才 Commit + Push，并建立只表示阶段验收的固定 Git Tag（不创建 Release）。不改写已推送历史。发现已验收模块回归时受控修复并复验。
- 全部阶段完成后独立跨模块集成验收和安装包真实升级验证。P0/P1 故障阻断正式发布；P2/P3 风险可接受且用户明确批准时才能列入已知问题。
- CI 偶发失败要保留原证据与原因调查；安全/权限/事务/数据完整性测试不能靠重跑一次通过放行。非关键不稳定测试只有用户事先批准、具备替代验证与恢复条件时才允许临时隔离，关键测试不得隔离绕过。
- 历史版本故障默认通过独立 `git worktree` + 测试数据库复现。先验证当前分支是否仍受影响，再按当前架构提出修改，必须获用户批准。修复过的有效缺陷原则上固化长期回归测试。
- 每正式发布版本先生成真实 NSIS 安装包验证：升级、迁移前备份、旧数据库、用户数据保留、MCP sidecar、授权和权限隔离、更新失败重试、构建产物/版本一致性。遵循仓库当前 `AGENTS.md` 与 Actions 发布机制；正式 Release 必须另行获得用户授权。
- 紧急热修复可精简非相关重复验证，但不可省略安全、数据完整性、相关回归、升级验证与用户最终确认。不自动远程回滚已安装客户端；程序回退和数据库恢复分开评估。

## 6. 容易误解的最终决议

| 议题 | 用户确认的最终规则 |
|---|---|
| 旧 MCP 接口 | **可在下一正式版本直接移除**，不要求保留 90 天；需明确影响与迁移说明，经用户批准。 |
| 原有两项匿名只读 | 新版必须认证；这是有意的安全不兼容变化。 |
| 磁盘缓存 | 不增加内容加密；使用 Windows 文件 ACL 并减少敏感落盘。不得把这一选择扩展至客户端凭证存储。 |
| 异常查询 | 只提供基础状态筛选；不做跨字段组合查询与关键词搜索。与事项的高级组合查询是不同模块。 |
| 故障导出校验 | 不生成额外哈希校验文件；**软件更新安装包的 SHA-256 digest 校验仍必须执行**。 |
| 阶段提交 | **先测试、用户验收，后 Commit / Push / 阶段 Tag，再进入下一阶段**，最终发布另行确认。 |
| 自动化恢复 | 既有授权内低风险技术恢复可自动；业务数据修复、授权调整、数据库恢复或结果不明写入重放严禁自动执行。 |
| 日历 | 现有工作日历仍为只读历史回顾，计划未来事项只能通过事项业务规则操作。 |
