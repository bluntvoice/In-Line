# 隔离测试与逐项验收设计（P0草案）

**状态：新增测试均为计划，未执行。** 现有基线测试的实际结果见PHASE-00。每条需求的专属用例编号为 `T-MCP-001` … `T-MCP-144`，场景、原文验收条件、拟实现位置逐行见追踪矩阵/CSV。工程流程类需求按文档/授权/Git证据验收，不能虚构为已经运行的单测。

## 1. 安全隔离

- 不读取用户生产 `%APPDATA%/in-line/inline.db` 来构造夹具；不用现有已安装主程序作为测试服务，不停止用户软件。
- 域/SQLite测试用临时目录 `Database::open_at`、合成事项、独立备份/安全库/任务/缓存根；仅debug/tests可覆盖路径，release不接受AI指定业务库路径。
- stdio测试使用实际新构建测试sidecar及隔离主服务；独立应用标识、Named Pipe名称、SID/机器绑定测试桩，生产身份和环境凭证不继承。清理先核对绝对目录在本次夹具根内，不递归清理共享TEMP或用户文件夹。
- Windows原生IPC、ACL、DPAPI和single-instance不能仅用mock宣称通过；至少实际同机多进程及拒绝路径测试。跨用户/跨机器复制和NSIS升级用VM/独立账户或第二测试设备，不能把同进程模拟冒充实机。
- UI逻辑优先现有隔离浏览器API夹具；焦点、原生窗口、后台启动、安装升级只在隔离安装或用户明确指定设备验收。
- 所有时限用可注入时钟，不真实等待7/30天或24小时；生产用真实期限、测试跨重启持久时间。性能运行使用合成数据，不上传真实事项。

## 3. 性能与资源验证

P1定义限流、最大并发、IPC包长及资源硬上限；P2快照/P5任务/P6缓存均设配额。使用1千/1万/10万合成事项及多轮事件，记录查询/第一页/任务取消时间、主进程内存峰值、快照空间、数据库锁等待和GUI输入响应。至少2个客户端交错读写及突发失败请求。

具体延迟/空间数值依据P1基线测量形成预算并提交用户验收，P0不凭空宣称性能达标。CI只做稳定小规模回归，较大基准单独记录硬件、构建SHA和数据规模；禁止将截断结果标记为完整来“优化”。

## 4. 证据规则与失败处理

- 每次命令保存命令/日期/构建SHA/退出码/实际数量、首次失败与后续调查；敏感字段清理后再入仓库。基线B1–B4原始输出仅现有合成测试和构建，没有用户业务日志。
- 新测试对应T-MCP编号或套件子用例；一测试可覆盖多条，但每条验收点都有可定位断言/步骤。矩阵填实际文件函数/测试名称/证据，不能只填“测试通过”。
- 关键安全/事务/数据失败即暂停阶段，查明根因并回归；非关键不稳定测试只有用户事先批准且有替代验证/期限/恢复条件才可隔离。禁止静默删断言/降低覆盖来放行。
- 历史版本默认独立Worktree+隔离库；先证当前仍受影响再申请迁移修复。长期保存已证缺陷回归；重构可替换测试但关键覆盖不能未经批准削弱。
- 最终P8跨阶段独立验收，P9真实安装/旧数据升级、认证重新配置与发布清单逐项通过；正式Release单独授权。热修保留安全/数据/相关回归/安装升级与用户验收，不能只拿CI重跑成功代替。
