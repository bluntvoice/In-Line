# 应用内检查更新 PRD

> **状态：已实现 · 待测试验收**
>
> **适用项目：In Line｜排着呢**
>
> **首次规划时间：2026-08**
>
> **最后更新：2026-08-28**

## 1. 功能背景

In Line 当前通过 GitHub Releases 提供 Windows 安装包。

用户升级版本时需要：

1. 自行打开 GitHub；
2. 查找最新 Release；
3. 判断是否高于当前版本；
4. 下载安装包；
5. 手动启动安装程序。

随着软件持续更新，该流程存在一定使用成本。

因此增加应用内「检查更新」功能，让用户能够直接在 In Line 中确认是否存在最新正式版本，并完成安装包下载。

---

# 2. 产品目标

该功能用于：

> 在不改变 In Line 日常纯本地使用方式的前提下，为用户提供主动、可控的版本检查和更新下载能力。

主要目标：

- 降低查找 GitHub Release 的操作成本；
- 避免用户误下载旧版本或错误安装包；
- 展示真实下载进度；
- 在下载完成并通过完整性校验后启动正式安装程序；
- 更新失败不得影响 In Line 正常使用。

---

# 3. 产品定位

第一版属于：

> **手动检查更新**

而不是后台自动更新。

只有用户明确点击：

> 检查更新

后，In Line 才访问 GitHub。

软件启动时不得自动：

- 检查；
- 下载；
- 安装更新。

该设计继续保持 In Line：

> 日常功能无需联网。

---

# 4. 功能入口

入口位于：

> 关于 In Line → 软件版本

当前版本号右侧增加：

> **检查更新**

按钮。

按钮样式应与关于页面现有：

> 复制地址

按钮保持一致，包括：

- 尺寸；
- 字号；
- 圆角；
- 边框；
- 背景；
- hover / active 状态。

仅将图标替换为更新或刷新类图标。

按钮不应成为页面的主要视觉焦点。

---

# 5. 检查状态

用户点击后，按钮应给予明确反馈。

## 正在检查

> 正在检查…

检查过程中避免重复触发。

## 已是最新版

> 已是最新版本

短暂提示后可恢复为：

> 检查更新

## 检查失败

> 检查更新失败，请稍后重试

失败后仍可重新检查。

网络错误不得影响关于页面及软件其他功能。

---

# 6. 更新来源

第一版仅使用：

> `bluntvoice/In-Line` 官方 GitHub Releases

并且仅接受：

- 正式 Release；
- 非 Draft；
- 非 Prerelease。

Beta、RC 等测试版本不进入普通更新通道。

---

# 7. 版本判断

远程最新版本必须高于本地当前版本时，才认为存在更新。

例如：

> 当前 v0.2.3
>
> 最新 v0.2.4

则提示更新。

如果：

> 当前 v0.2.4
>
> 最新 v0.2.4

或者：

> 当前 v0.2.5
>
> 最新 v0.2.4

均应视为无需更新。

不得提供自动降级。

版本比较必须遵循正常版本号语义，避免简单字符串比较导致错误。

---

# 8. 安装包选择

仅下载适用于当前 In Line Windows x64 安装方式的正式 NSIS 安装包。

不得：

- 任意选择 Release 中第一个文件；
- 下载未知 EXE；
- 根据 Release 正文中的普通链接下载文件；
- 从第三方镜像自动下载。

如果 Release 中不存在正确安装包：

> 未找到适用于当前系统的更新安装包

并停止更新流程。

---

# 9. 下载流程

发现新版本后，用户无需再次前往浏览器。

In Line 自动：

1. 获取正式安装包；
2. 下载至系统临时目录；
3. 展示实时下载进度；
4. 完成文件完整性校验；
5. 校验成功后启动安装程序。

安装包不得默认写入：

- Downloads；
- 桌面；
- In Line 安装目录；
- In Line 数据库目录。

---

# 10. 更新进度悬浮窗

下载开始后，在屏幕右下角显示独立的小型更新进度悬浮窗。

该窗口与现有事项悬浮窗完全独立。

不得：

- 替换现有事项悬浮窗内容；
- 改变原悬浮窗展开/迷你状态；
- 占用现有队列展示逻辑。

更新进度窗属于临时系统状态提示。

下载中关闭进度窗时，仅隐藏窗口，下载任务继续；用户再次在关于页面点击检查更新时恢复显示当前进度。

---

# 11. 更新进度窗内容

下载过程中至少展示：

> In Line 正在更新

以及：

- 目标版本；
- 已下载大小；
- 总大小（能够获取时）；
- 下载百分比（能够可靠计算时）；
- 进度条。

例如：

> In Line 正在更新
>
> v0.2.4
>
> 6.2 MB / 10.1 MB · 62%

如果无法可靠获得总大小：

- 可以显示已下载大小；
- 使用不确定进度表现；
- 不允许伪造百分比。

---

# 12. 下载阶段状态

更新悬浮窗应能够表达至少以下状态：

### 下载中

> 正在下载更新…

### 校验中

> 正在校验更新包…

### 准备安装

> 下载完成，正在启动安装程序…

### 下载失败

> 更新下载失败

并提供重新尝试或关闭提示的能力。

---

# 13. 完整性校验

下载完成后必须进行 SHA-256 完整性校验。

校验依据为 GitHub Release Asset 官方提供的 SHA-256 digest。

只有：

> 本地安装包 SHA-256
>
> = GitHub Release Asset digest

时才允许启动安装程序。

如果：

- digest 缺失；
- digest 类型不是 SHA-256；
- 本地文件计算结果不一致；

均不得继续自动执行安装包。

提示：

> 更新包校验失败，请重新下载

不得提供：

> 忽略校验继续安装

之类的绕过入口。

---

# 14. 安全边界

SHA-256 校验主要用于：

- 检测文件下载损坏；
- 确认下载后的文件与 GitHub Release Asset 内容一致。

该机制不能防御：

> GitHub 仓库或发布权限本身被攻击者完全控制。

因此项目文档不得将其描述为：

- 数字签名验证；
- 独立可信签名；
- 绝对安全更新。

当前功能应准确描述为：

> GitHub Release 来源限制 + SHA-256 完整性校验。

---

# 15. 临时文件

更新安装包统一放置于系统临时目录下的 In Line 专属更新区域：

> `%TEMP%\In-Line\updates\v版本号\`

用户不需要自行管理安装包。

不要求当前 In Line 在安装完成以后继续运行后台任务删除安装程序。

后续更新检查可以适当清理自身遗留的旧更新临时文件。

不得清理 In Line 之外的系统临时内容。

---

# 16. 安装方式

第一版不采用完全静默安装。

下载成功并通过完整性校验后：

1. 显示即将安装的状态；
2. 自动启动现有正式 NSIS 安装程序；
3. 用户看到正常安装界面；
4. 安装程序成功启动后，当前 In Line 退出；
5. 用户按正常安装流程完成升级。

不得自行通过程序代码覆盖安装目录文件。

---

# 17. 软件退出原则

必须保证：

> 安装程序成功启动后，当前 In Line 才退出。

如果安装程序无法启动：

- In Line 保持运行；
- 用户可以继续正常工作；
- 提示启动安装失败；
- 允许重新尝试。

避免出现：

> In Line 已退出，但安装程序实际上没有成功启动

的情况。

---

# 18. MCP 兼容

In Line 安装包当前包含 MCP 伴随程序。

更新安装时应继续兼容现有安装逻辑，尽可能避免因 MCP 进程仍被外部 AI 客户端占用而导致安装失败。

不得为了安装更新直接关闭：

- Codex；
- ChatGPT；
- 其他外部 AI 客户端。

只应处理 In Line 自身相关伴随进程。安装前允许进行一次有界复查，避免伴随进程被外部客户端立即重新拉起。

---

# 19. 网络失败原则

以下问题均应安全失败：

- 无网络；
- GitHub 无法访问；
- 请求超时；
- GitHub 服务异常；
- API 限流；
- 下载中断；
- Release 不存在；
- 安装包不存在；
- SHA-256 信息缺失；
- 校验失败；
- 临时目录写入失败；
- 安装程序启动失败。

任何更新失败不得影响：

- 待办队列；
- 办理记录；
- 数据库；
- 统计；
- 备份；
- MCP；
- 软件启动。

---

# 20. 隐私与联网说明

In Line 的事项管理、统计、备份等日常功能继续完全在本地运行。

只有用户主动点击：

> 检查更新

时才访问 GitHub Releases。

更新功能不得上传：

- 事项信息；
- 联系人；
- 统计数据；
- 数据库；
- 使用记录。

---

# 21. 第一版明确不包含

当前版本不实现：

- 启动时自动检查更新；
- 后台周期检查；
- 自动下载未经过用户主动触发的更新；
- 强制更新；
- 完全静默安装；
- Beta / Prerelease 通道；
- Tauri 官方 Updater 私钥签名体系；
- 用户自定义更新源；
- 第三方镜像；
- 应用内完整 Release Notes 阅读器。

---

# 22. 验收标准

至少应验证以下场景：

1. 当前版本已是最新；
2. GitHub 存在更高正式版本；
3. GitHub 版本低于当前本地版本；
4. 两位数版本号能够正确比较；
5. Release 中存在多个 Asset 时选择正确安装包；
6. 正常下载并展示真实进度；
7. 无法获取总大小时不显示虚假百分比；
8. SHA-256 校验成功；
9. SHA-256 校验失败；
10. digest 缺失；
11. 网络中断；
12. 临时目录写入失败；
13. installer 启动成功；
14. installer 启动失败时 In Line 不退出；
15. 原事项悬浮窗与更新悬浮窗同时存在且互不影响；
16. 检查更新失败后软件其他功能继续正常使用；
17. 下载中隐藏进度窗后任务继续，再次检查可恢复显示。

---

# 23. 后续可评估方向

第一版稳定后，可以根据使用情况考虑：

- 启动后仅提示存在新版本；
- 用户自行决定是否下载；
- Release Notes 简要预览；
- 下载取消与恢复；
- 更完整的更新缓存管理；
- Windows 代码签名；
- 更强的独立更新签名体系。

上述内容属于潜在优化方向，不代表当前开发承诺。
