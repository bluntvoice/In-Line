## A 的可行性边界与最小步骤

### 1. 先隔离准备阶段，不按观察到的状态猜测可终止性

当前 `install-guard.ps1` 同次启动内先 `Add-Type`，随后直接进入 `Guard.Run`；父安装器没有可靠的“编译完毕但禁止进入事务”控制边界。即使某一时刻没看到事务目录，helper 下一刻仍可能进入预检或修改。**因此现状下不能证明对该进程超时结束是安全的。**

可评估的最小结构是：准备调用只允许编译本次私有目录内的固定源码/临时程序集并退出，不接收安装目标路径、不调用 Guard 文件/元数据事务；确认其成功和退出后，父安装器才显式发起事务调用。临时程序集如被使用，必须绑定本包源码、架构与摘要，在载入前检查路径、归属和完整性；不使用跨安装共享的编译缓存。

这样才能把“可以禁止本次事务启动”建立在程序职责上，而不是旧进度消息或缺失文件上。准备取消和事务启动的竞态也必须有明确的先后结果：已接受取消就不得再启动事务；已经进入事务则转为协作取消，不再走准备阶段结束路径。

### 2. 有限等待不等于安全取消已完成

父安装器可以设置一次等待的有限区间，但超时只表示尚未收到完成确认。`nsExec /TIMEOUT` 按输出空闲时间计时，不能当作事务总时限或子进程树已退出的证明。[NSIS 官方说明](https://nsis.sourceforge.io/NsExec_plug-in)。

A 的准备阶段结束必须同时证明：该调用不可能进入文件事务、目标进程身份确定、编译后代归属可控、完成退出已经确认、不会残留可继续触及目标安装目录的任务。只观察 PowerShell PID 退出不够；Windows 不因父进程终止而自动终止全部子进程。[Windows 进程终止说明](https://learn.microsoft.com/en-us/windows/win32/procthread/terminating-a-process)。

现有 nsExec 接口没有给本项目提供已验证的进程树管理与取消协议。应先验证能否复用现有工具满足上述条件；若必须使用公开 Win32 进程句柄或 Job Object，应另行列清具体改动及风险，不能擅自换成新启动器、额外 PowerShell 看守层或服务。Job Object 只是可能的公开能力，不是本轮已选架构；其子进程继承/脱离、嵌套 Job 和企业限制都须验证。尤其不得把“父退出即杀全部成员”的设置套到已经写入或回滚的事务 helper。[Job Object 文档](https://learn.microsoft.com/en-us/windows/win32/procthread/job-objects)。

若不能确认准备进程树已安全退出，就显示“准备停止尚未确认”，保持受控等待，不正常退出失败后放任 helper 将来进入事务。无法满足这一点时，A 的有界取消分支判为不可用，停止扩展并回到 B 的技术边界。

不在本方案中指定 15 秒、60 秒等生产阈值。后续须先收集启动/编译耗时，再确认等待、提示和取消的不同阈值。有限 API 等待也不是操作系统、驱动、休眠和磁盘异常下的绝对墙钟保证。[Windows 等待接口语义](https://learn.microsoft.com/en-us/windows/win32/api/synchapi/nf-synchapi-waitforsingleobject)。

### 3. 事务内只增加少量协作取消点

可候选的位置：进入受管文件预检前、备份及 journal 准备完成而尚未替换前、固定五文件之间、元数据应用前/返回后。具体位置需逐一检查当前 `mutated`、`prepared`、占位文件、关闭时删除标志及元数据句柄状态，不能机械插入异常。

取消请求只表示“申请停止”，helper 在安全点确认接受后，才进入已有错误恢复路径：

1. 尚未替换文件时撤销本轮新建占位和准备状态，确认资源释放。
2. 已修改时继续持有原句柄及备份，执行 R1 的文件、快捷方式及注册值恢复和回读。
3. 恢复期间禁止再次取消或超时强杀；用户再次点击不能中断恢复。
4. 恢复确认、句柄释放、helper 退出和父进程结果必须一致；恢复失败保留 journal/备份和屏障，明确报告“恢复未确认”。

阻塞在一次写入、flush、COM 或内核调用时，协作取消不能保证立刻获得执行机会。恢复自身也可能阻塞，因此**不承诺事务/回滚有限时刻必然完成**。

必须定义一个停止接受新取消请求的完成边界；已进入 finalize 时不能把取消按钮当作可强行撤销。若取消与完成竞态发生，返回“已接受并恢复”“已进入完成确认”或“恢复未确认”的真实结果，不能只因 UI 收到点击就声称已取消。

### 4. 用户状态与阶段记录

建议显示的阶段只有“准备运行环境”“预检/备份”“修改程序及元数据”“恢复中”“完成确认”“状态无法确认”。显示等待时长和最后确认阶段，不显示虚构百分比；没有新消息时不得断言仍在某条具体写入。

取消请求、取消接受、恢复确认、helper 退出是四件不同的事。应明确提示：正常等待期间不要再开安装器；恢复未确认时不要启动该目录、删除备份或清除事务标记。GUI 的普通关闭会隐藏到托盘；退出路径与独立 MCP 占用应分别说明，但不引导终止当前正式连接。

当前 `ExecToStack` 到返回时才提供捕获文本，尚不能据此证明等待期间有可响应的取消 UI。NSIS 的消息调度、日志传递和结果文件协议属于 A 的可行性验证项；不能仅改文案便宣称实时状态和可取消已完成。

**最小版不必新增持久化逐阶段状态机。** 可先用本次操作标识、进程身份和仅本次私有目录的诊断记录表达最后确认阶段，保留原 journal 作为恢复依据。诊断记录不授予写入或终止权限，不能替代句柄及实际状态核验。

若要求安装器异常关闭后仍可准确追踪阶段，则需要额外持久化记录：格式版本、阶段序号、原子更新、ACL、损坏处理及旧 journal 兼容。当前 `Clean` 会拒绝未知恢复文件，新侧文件也会影响清理白名单；不能随手往事务目录写一个 JSON 就视为安全。这个扩展估计另需约 2～4 工程日验证，并可能增加崩溃窗口与同步风险，应单独批准。即使记录完整，也不提供断电原子性或安全强杀依据。

## B 的明确限制与支持规则

保持当前阻塞等待和普通错误恢复路径，不加超时、不新增取消协议、进程容器、阶段格式或服务。本轮仅将限制和支持规则整理成可审阅文档，不改产品提示代码。

- 长时间无响应时不能保证自动退出，用户不能据此认定安装已经失败或完成。
- helper 仍存活时不支持强行结束安装器后立即重新安装，也不支持按名称结束全部 PowerShell、In-Line 或 MCP。
- 活跃进程尚在时保持其既有锁和恢复资源；进程已退出后不能声称仍持有句柄。保留的 journal/备份/目录屏障与活跃锁是不同机制。
- 编译前期可能尚无事务目录或备份；这不能用来推断“关闭安装器不会留下稍后执行的 helper”。已进入事务后的保留屏障也不等于自动恢复成功。
- 真挂起、父进程异常结束、驱动/磁盘异常、真实企业执行限制仍属于未解决兼容性边界；不以文档说明替代技术修复。

选择 B 表示暂缓增加复杂度，不表示这些限制已经满足原有产品目标。如果“所有 helper 挂起都必须自动且安全有界退出”成为不可豁免的发布条件，B 不满足它，发布仍须阻断。
